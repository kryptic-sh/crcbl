# Topic 42 — Steamworks (`crcbl-steam`)

Steam support as a workspace crate: an FFI wrapper over the Steamworks SDK's
flat C API that is idiomatic Rust at the surface — an event queue drained once
per frame, typed tokens for asynchronous calls, errors that name the failure —
and hand-written FFI underneath, in the shape `crcbl-shell` already uses for
libxcb and libwayland-client. This document fixes how the SDK is obtained (it
cannot be vendored), how the crate stays green on a CI that has no Steam client
and a workspace that compiles every crate on four targets, how Steam's callback
model maps onto the engine's frame loop, and which interfaces land in which
order. Like topics 11–41 its number is identity, not sequence: no roadmap phase
is claimed here, and registering the topic row in `00-overview.md` and a phase
in `ROADMAP.md` belongs to the slice that starts the work.

Two findings shape everything below, so they come first:

- **The SDK cannot enter the repo, and CI can never run it.** Valve's access
  agreement licenses redistribution of `redistributable_bin` in object form
  alongside a shipped game and nothing else; the headers are licensed for local
  reproduction "solely to develop the Licensee Software". The SDK zip itself is
  behind a partner-site login (verified: the download URL answers a 302 to the
  login page). So there is no vendored header, no `build.rs` that links a
  `.lib`, and no CI job that talks to Steam — the whole design has to be
  arranged so that what CI _can_ check is real and what it cannot check is
  stated rather than faked.
- **Steam is the first thing in the project's history that could reopen topic
  27's tier 3.** The 2026-08-09 roadmap correction cut hosted token auth and
  `crcbl-mint` because "no hosted infrastructure exists anywhere in the
  project". Steam is a backend the project does not have to run:
  `GetAuthSessionTicket` mints an identity proof on the client and
  `BeginAuthSession` validates it on a server, with Valve operating the trust
  root. The argument is developed in the auth section below.

## What the flat API actually is

Everything in this section was read from the SDK's own headers on 2026-08-22 —
via the header mirror Steamworks.NET maintains for its code generator
([rlabrecque/Steamworks.NET `CodeGen/steam`](https://github.com/rlabrecque/Steamworks.NET/tree/master/CodeGen/steam)),
because the SDK zip itself is login-gated — and from Valve's public API pages.
The mirror tracks a current SDK (1.6x); every version-suffixed name below must
be re-read from the SDK the implementer actually downloads, which is what the
provenance rule in the binding section is for.

- **`steam_api_flat.h` is a plain-C mirror of every interface method**,
  auto-generated by Valve, "for binding to other languages"
  ([API overview](https://partner.steamgames.com/doc/sdk/api)). Methods take the
  interface pointer explicitly and use C types throughout — `CSteamID` crosses
  as `uint64_steamid`:

  ```c
  S_API uint64_steamid SteamAPI_ISteamUser_GetSteamID( ISteamUser* self );
  S_API bool SteamAPI_ISteamUserStats_SetAchievement( ISteamUserStats* self, const char * pchName );
  S_API bool SteamAPI_ISteamRemoteStorage_FileWrite( ISteamRemoteStorage* self, const char * pchFile, const void * pvData, int32 cubData );
  S_API SteamAPICall_t SteamAPI_ISteamUGC_SubmitItemUpdate( ISteamUGC* self, UGCUpdateHandle_t handle, const char * pchChangeNote );
  ```

- **Interface pointers come from version-suffixed accessors**, one per interface
  per ABI revision — as read from the mirror: `SteamAPI_SteamUser_v023()`,
  `SteamAPI_SteamFriends_v018()`, `SteamAPI_SteamUtils_v011()`,
  `SteamAPI_SteamUserStats_v013()`, `SteamAPI_SteamApps_v009()`,
  `SteamAPI_SteamRemoteStorage_v016()`, `SteamAPI_SteamUGC_v021()`,
  `SteamAPI_SteamInput_v007()`, `SteamAPI_SteamMatchmaking_v009()`,
  `SteamAPI_SteamNetworkingSockets_SteamAPI_v013()`. The suffix is the contract:
  an accessor that exists returns an interface with exactly that vtable layout,
  and a Steam client too old to have it fails at lookup rather than handing back
  the wrong table.
- **Initialisation has a flat entry point that skips version checking, and an
  internal one that does the checking.** `steam_api.h` is explicit that
  dynamic-loading bindings are what `SteamAPI_InitFlat` exists for, and equally
  explicit about what it does not do:

  ```c
  // Same usage as SteamAPI_InitEx(), however does not verify ISteam* interfaces are
  // supported by the user's client and is exported from the dll
  S_API ESteamAPIInitResult S_CALLTYPE SteamAPI_InitFlat( SteamErrMsg *pOutErrMsg );
  S_API ESteamAPIInitResult S_CALLTYPE SteamInternal_SteamAPI_Init( const char *pszInternalCheckInterfaceVersions, SteamErrMsg *pOutErrMsg );
  ```

  The C++-only `SteamAPI_InitEx` is an inline that calls
  `SteamInternal_SteamAPI_Init` with a `"\0"`-joined list of every
  `STEAM*_INTERFACE_VERSION` string baked in at compile time. That is the
  version validation, and it is available to us: **`crcbl-steam` calls
  `SteamInternal_SteamAPI_Init` with the exact accessor-version list its
  bindings were generated against**, so a client that cannot honour those
  versions fails init with `k_ESteamAPIInitResult_VersionMismatch` and an
  English `SteamErrMsg` (`typedef char SteamErrMsg[1024]`) instead of succeeding
  into undefined vtables. `ESteamAPIInitResult` is
  `OK = 0, FailedGeneric = 1, NoSteamClient = 2, VersionMismatch = 3`.

- **Manual dispatch replaces the C++ callback machinery entirely.** The classic
  path — `STEAM_CALLBACK`, `CCallback`/`CCallbackBase` vtables,
  `SteamAPI_RunCallbacks` — exists for C++ code. The header offers a second,
  lower-level path and forbids mixing them ("If you use the manual callback
  dispatch, you must NOT use: SteamAPI_RunCallbacks … STEAM_CALLBACK,
  CCallResult, CCallback, or CCallbackManual"):

  ```c
  S_API void S_CALLTYPE SteamAPI_ManualDispatch_Init();
  S_API void S_CALLTYPE SteamAPI_ManualDispatch_RunFrame( HSteamPipe hSteamPipe );
  S_API bool S_CALLTYPE SteamAPI_ManualDispatch_GetNextCallback( HSteamPipe hSteamPipe, CallbackMsg_t *pCallbackMsg );
  S_API void S_CALLTYPE SteamAPI_ManualDispatch_FreeLastCallback( HSteamPipe hSteamPipe );
  S_API bool S_CALLTYPE SteamAPI_ManualDispatch_GetAPICallResult( HSteamPipe hSteamPipe, SteamAPICall_t hSteamAPICall, void *pCallback, int cubCallback, int iCallbackExpected, bool *pbFailed );
  ```

  Each drained message is a `CallbackMsg_t` —
  `{ HSteamUser m_hSteamUser; int m_iCallback; uint8 *m_pubParam; int m_cubParam; }`
  — an integer id plus a borrowed byte buffer, valid until `FreeLastCallback`.
  Asynchronous method results arrive through the same loop as callback id
  `SteamAPICallCompleted_t::k_iCallback` (`k_iSteamUtilsCallbacks + 3`, with
  `k_iSteamUtilsCallbacks = 700`), carrying
  `{ SteamAPICall_t m_hAsyncCall; int m_iCallback; uint32 m_cubParam; }`; the
  payload is then fetched with `GetAPICallResult`. `SteamAPICall_t` is
  `typedef uint64`, `0` reserved as `k_uAPICallInvalid`; `HSteamPipe` and
  `HSteamUser` are `int32`. **This is the ABI `crcbl-steam` binds — bytes and
  integers on a pipe we poll, no C++ vtables registered with anyone, and no
  foreign code calling back into Rust.** Valve's own overview says manual
  dispatch "is especially useful for binding layers".

- **Callbacks fire on the thread that pumps them** — with manual dispatch there
  is no firing at all, only the drain loop, so the thread question reduces to
  "which thread drains the pipe", answered in the pump section.
- **The SDK ships `steam_api.json`**, a machine-readable description of every
  interface, method, callback struct and constant, "to allow you to create
  bindings for other languages more easily"
  ([API overview](https://partner.steamgames.com/doc/sdk/api)). It is the input
  the declaration-drift gate below reads.
- **Version facts.** Current SDK is 1.63 (2026-01-29:
  [announcement](https://steamcommunity.com/groups/steamworks/announcements/detail/627817201164877826)
  — adds linuxarm64/androidarm64 libs, removes `ISteamMusicRemote`); 1.61
  removed `RequestCurrentStats` — stats now arrive without being asked
  ([1.61 announcement](https://steamcommunity.com/groups/steamworks/announcements/detail/4480612432780198328))
  — and 1.62 removed `ISteamFriends::SetPersonaName` and `GetUserRestrictions`
  ([1.62 notes](https://steamdb.info/patchnotes/17946746/)). The `steamworks-rs`
  README's table pins its git head to SDK 1.64, which this research could not
  find an announcement for; treat "1.63 or 1.64" as the current range and read
  the number off the zip.

## The licence, and how a build gets the SDK

What the
[SDK Access Agreement](https://partner.steamgames.com/documentation/sdk_access_agreement)
actually permits, in its own words: Valve grants a licence to "reproduce and
distribute the part of the SDK provided inside the folder named
redistributable_bin (the 'SDK Redistributables') along with the Licensee
Software in object code form", and to "use and locally reproduce the SDK in
source code form, solely to develop the Licensee Software". Nothing grants
publication of the headers, and this repo is public under MIT. Consequences:

- **Nothing from the SDK is committed.** No header, no `steam_api.json`, no
  `libsteam_api.so`. The repo carries only our own declarations of the C ABI
  (see the next section for what that means and the decision it needs).
- **A developer supplies the SDK themselves**: download the zip from the partner
  site (any Steam account that has accepted the agreement — the URL is
  login-gated, verified 2026-08-22), unzip anywhere, and point the engine at it
  with one environment variable, `CRCBL_STEAM_SDK=/path/to/sdk`. Nothing reads
  it at _build_ time; it is used by (1) the declaration-drift gate, which reads
  `public/steam/steam_api.json`, and (2) the runtime library search below.
- **At runtime the crate `dlopen`s the redistributable**, exactly as `crcbl-vk`
  loads `libvulkan.so.1` and for the same three reasons its crate docs give: a
  fallible entry in a fall-through list, one binary across a CI matrix that
  mostly lacks the library, and the cost is one `dlopen`. Search order: next to
  the executable (where a shipped build must place it — Valve's documented
  layout), then `$CRCBL_STEAM_SDK/redistributable_bin/<platform>/`. The names
  are `libsteam_api.so` (linux64), `steam_api64.dll` (win64),
  `libsteam_api.dylib` (osx, fat x64+arm64), per the
  [API overview](https://partner.steamgames.com/doc/sdk/api)'s linking section.
- **Absent is ordinary.** No library found, or found but `NoSteamClient`, is an
  `Err` a game turns into "run without Steam" — never a dead process in `ld.so`,
  never a panic. `deny.toml` never sees any of this: no crate, no licence, no
  source enters the dependency graph.
- **Shipping** (far future, needs a registered app): the game's depot carries
  the redistributable next to the executable — the one distribution the
  agreement licenses — and `steam_appid.txt` is a dev-only file that must not
  ship ("Do not ship this with your builds",
  [API overview](https://partner.steamgames.com/doc/sdk/api)).

## The crate and its gating

A new crate, `crcbl-steam`, joining the workspace the standard way: globbed
member, pinned in `[workspace.dependencies]` with `path` **and** `version` (the
bare `{ path }` form is a wildcard to `cargo deny`), minimal manifest inheriting
workspace fields, `thiserror` as the only dependency. `dlopen`/`dlsym` are
declared against libc as `crcbl-shell`'s `x11/ffi.rs` does; the Windows side
declares `LoadLibraryW`/`GetProcAddress` as `crcbl-shell`'s `win32/ffi.rs`
already models. **The recommended route adds zero new dependencies.**

Target gating follows the `crcbl-dx12` pattern exactly — there is no
`#![cfg(...)]` crate root anywhere in this workspace, and none here:

- Every module that touches the FFI is
  `#[cfg(any(target_os = "linux", target_os = "windows", target_os = "macos"))]`
  — the three platforms the SDK ships redistributables for and the three this
  workspace's CI can type-check. On `wasm32` (and anything else) the crate is
  its documentation and no public items, which is precisely how `crcbl-mtl` is
  absent off macOS: "the absence is expressed by the crate having no public
  items, not by a caller testing the platform". Nothing above the crate ever
  writes `cfg(target_os)` to ask about Steam.
- Pure-logic modules — the callback id tables, the decode of callback bytes, the
  call registry — are `#[cfg(any(..., test))]` so `cargo test` on Linux
  exercises them regardless, the same trick `crcbl-dx12` uses for its arithmetic
  and `crcbl-shell` for `win32`.
- Platform docs rule: an item absent on some target is named in backticks in
  rustdoc, never intra-doc-linked, because `cargo doc` is a `-D warnings` gate
  on targets where it does not exist.
- **CI changes, all three cheap:** the crate joins the wasm job's umbrella
  automatically (it compiles empty there — no exclusion, the deny-list stays at
  two); it must be **added to the "type-check the platform backends" step**
  alongside `crcbl-mtl`/`crcbl-dx12`
  (`cargo clippy -p crcbl-steam --target aarch64-apple-darwin` and
  `--target x86_64-pc-windows-msvc`, plus the matching `cargo doc` lines),
  because its macOS and Windows halves are real code compiled by no other job;
  and the ordinary Linux jobs cover the rest. `--all-features` everywhere is
  unaffected: no feature requires the SDK, because nothing requires the SDK to
  _build_.
- The umbrella exposes it as `crcbl/Cargo.toml`'s existing optional-dep shape:
  `steam = ["dep:crcbl-steam"]`, mirroring `scene = ["dep:crcbl-scene"]`, and a
  `pub use crcbl_steam as steam;` behind it.

## The binding route — presented, not decided

Three ways to speak this ABI. The recommendation is (a); adopting (b) would add
a dependency, which is the user's call by standing rule, and (a)'s licence
posture is its own user call (decision list below).

- **(a) Hand-written flat-API declarations + runtime `dlopen` — recommended.**
  The `crcbl-shell` pattern applied verbatim: a `prototype` module where every
  `type` carries the C declaration it was copied from in its doc comment plus
  **the SDK version it was read from**, a `symbol!` macro that `dlsym`s and
  reports the missing name, a `Lib` struct of typed function pointers behind a
  `OnceLock`. Scope makes this tractable: the flat header declares on the order
  of a thousand functions, but the slices below bind a few dozen at a time, and
  only what a slice uses is declared — the house rule against speculative
  surface applies to FFI too. Two checks keep it honest: the version handshake
  at init (`SteamInternal_SteamAPI_Init` with our exact accessor list, above),
  and a **declaration-drift gate** — an `#[ignore]`d test that, when
  `CRCBL_STEAM_SDK` is set, parses the SDK's own `steam_api.json` and asserts
  every name `Lib` binds exists with the arity and types we declared. That gate
  genuinely fails: point it at a newer SDK whose accessor version moved and it
  goes red. Cost: the declarations are ours to maintain, one interface at a
  time.
- **(b) `steamworks-rs`**
  ([Noxime/steamworks-rs](https://github.com/Noxime/steamworks-rs), 0.13.x,
  actively maintained, MIT/Apache "except for the files in
  `steamworks-sys/lib/steam/`"). What it buys: a decade of accumulated ABI
  knowledge and a safe `register_callback` surface. What it costs here, and why
  it is not recommended: `steamworks-sys` **vendors Valve's SDK inside the
  published crate** and its `build.rs` emits
  `cargo:rustc-link-lib=dylib=steam_api` — a link-time `DT_NEEDED` on every
  binary that enables it, which is exactly the failure mode `crcbl-vk`'s loader
  decision exists to avoid (a machine without the library dies in the dynamic
  linker before `main`, before any fall-through can run). Its callback closures
  also dispatch during `run_callbacks` rather than through an event queue, so
  the engine would wrap its wrapper to get the frame-loop shape below; its
  bindings are bindgen output regenerated only under a `rebuild-bindings`
  feature; and a workspace whose windowing speaks raw libwayland by choice does
  not want its one Steam dependency to be the largest foreign surface in the
  tree. Verified from its `build.rs` and manifest 2026-08-22.
- **(c) `bindgen` at build time against `$CRCBL_STEAM_SDK`.** Correct-by-
  construction signatures, but every contributor and every CI job now needs
  libclang _and the SDK_ to build the workspace — which CI cannot have. A
  variant that pregenerates and commits bindgen output collapses into (a) with
  worse provenance (bindgen output of the whole header is a derived copy of the
  header; targeted hand declarations of the functions we call are ABI facts).
  Rejected.

## Initialisation, shutdown, and what the types forbid

```rust
pub struct AppId(pub u32);

/// A live connection to the Steam client. Owns the loaded library, the
/// interface pointers, the pending-call registry and the event queue.
/// Deliberately `!Send + !Sync`: one owner, one pump thread.
pub struct Steam { /* Lib, HSteamPipe, interface pointers, registry, queue */ }

impl Steam {
    /// Ships-through-Steam guard; call before `init` in release builds.
    /// Loads the library only transiently; `Ok(true)` means "quit now,
    /// Steam is relaunching us".
    pub fn relaunch_via_steam(app: AppId) -> Result<bool, InitError>;

    /// Load the redistributable, `SteamInternal_SteamAPI_Init` with the
    /// bound accessor-version list, `SteamAPI_ManualDispatch_Init`, cache
    /// the interface pointers. One call per process.
    pub fn init(app: AppId) -> Result<Steam, InitError>;
}

impl Drop for Steam {
    /// `SteamAPI_Shutdown`. Nothing to poison: every borrow is gone by here.
    fn drop(&mut self) { /* … */ }
}
```

The lifetime rules are enforced by shape, not by comment:

- **Use-after-shutdown is unrepresentable.** Shutdown _is_ `Drop`. Every
  interface surface is an accessor struct borrowing `&Steam`
  (`pub struct Friends<'a>(…)`), every async token is redeemed through
  `&mut Steam`, so the borrow checker retires all of them before drop can run.
  There is no `shutdown(&mut self)` method precisely because it would have to
  document "don't use the accessors after this" instead of forbidding it.
- **Interface pointers are resolved once, at init, and never re-fetched.** They
  are valid for the life of the pipe; they live in `Steam`; they die with it. No
  global, no `OnceLock`d interface pointer that could outlive shutdown — only
  the `Lib` (the loaded module and its symbols) is process-cached, because a
  `dlopen`ed library with live pointers into it is never safely unloaded (the
  same argument `crcbl-shell` makes; it leaks the handle on purpose).
- **`Steam` is `!Send`.** Valve documents the API as callable cross-thread, but
  the pipe's callback stream is drained where `pump` runs, and handing
  interfaces to other threads buys nothing this engine wants — work that belongs
  off-thread goes through `crcbl-jobs` and comes back as data. Keeping the whole
  surface on the owning thread also makes `SteamAPI_ReleaseCurrentThreadMemory`
  irrelevant. If a real need for a cross-thread call appears, that is a
  deliberate later change with its own argument, not a `Send` slapped on.
- **`crcbl_core::Handle<T>` is deliberately not used for Steam's ids.** The
  generational handle exists for pools _we_ allocate from, where the generation
  detects our own slot reuse. `CSteamID`, `SteamAPICall_t`, `HAuthTicket`, UGC
  handles are issued by Valve's process with their own semantics; wrapping them
  in `Handle` would fabricate a generation nothing checks — a check that cannot
  fail. They are newtypes over the exact C width (`SteamId(u64)`, `ApiCall(u64)`
  internal, `AuthTicketHandle(u32)`), `0` meaning invalid where Valve says it
  does (`k_uAPICallInvalid`). The one place a generational handle _would_ fit —
  our own pending-call registry — is keyed by `SteamAPICall_t` itself, because
  Valve's id is already unique per call and the registry must look up by it.

`InitError` follows house style — every variant a distinct, documented failure:

```rust
#[derive(Debug, thiserror::Error)]
#[non_exhaustive]
pub enum InitError {
    /// The redistributable was not found beside the executable or under
    /// `CRCBL_STEAM_SDK`. Carries every path tried and the loader's own
    /// message, so the log line says where to put the file.
    #[error("no steam_api library: tried {tried:?}: {dl_error}")]
    NoLibrary { tried: Vec<PathBuf>, dl_error: String },

    /// The library loaded but lacks a symbol we bind — an SDK older than the
    /// declarations. Names the symbol.
    #[error("steam_api has no symbol {0}")]
    NoSymbol(&'static str),

    /// Steam answered `k_ESteamAPIInitResult_NoSteamClient`: the client is
    /// not running or the app id is unknown. The message is Valve's own
    /// `SteamErrMsg`, English, for the log — not for parsing.
    #[error("steam client unavailable: {0}")]
    NoSteamClient(String),

    /// `k_ESteamAPIInitResult_VersionMismatch`: the running client cannot
    /// honour an interface version these bindings were generated against.
    #[error("steam client version mismatch: {0}")]
    VersionMismatch(String),

    /// `k_ESteamAPIInitResult_FailedGeneric`, message attached.
    #[error("steam init failed: {0}")]
    Failed(String),
}
```

## The pump — manual dispatch onto the frame loop

Steam's model and the engine's frame already agree: `SteamAPI_RunCallbacks` is
documented as "most games call this once per render-frame", and this engine has
exactly one place both loop drivers pass through. The design maps manual
dispatch onto it:

```rust
impl Steam {
    /// Drain the pipe: `SteamAPI_ManualDispatch_RunFrame`, then the
    /// GetNextCallback / FreeLastCallback loop. Callback payloads are decoded
    /// to `SteamEvent`s in the queue; `SteamAPICallCompleted_t` messages are
    /// routed to the pending-call registry. Once per frame.
    pub fn pump(&mut self);

    /// Drain the decoded events. The frame's idiom: pump, then drain, then act.
    pub fn events(&mut self) -> impl Iterator<Item = SteamEvent> + '_;
}

#[non_exhaustive]
pub enum SteamEvent {
    /// The overlay opened or closed — the standing pause cue.
    OverlayActivated { active: bool },
    /// Stats/achievements for the current user arrived or stored.
    UserStatsStored { result: SteamResult },
    UserAchievementStored { name: String },
    // …grows one variant per slice, beside the decode table.
}
```

- **Why a drained queue and not closures or channels:** closures registered
  per-callback are `steamworks-rs`'s shape and the borrow-checker's least
  favourite (callbacks re-entering `&mut` engine state from inside `pump`);
  channels would put a second thread and a `Send` bound where none is needed.
  The engine already has the idiom: `shell.pump(&mut |event| …)` feeds an input
  router once per frame, and `crcbl-store`'s browser backends are "resident
  caches with an out-of-band fill" whose asynchrony lives in a request/deliver
  queue. A drained `SteamEvent` queue is the same shape third time over.
  `crcbl-jobs` is not involved: the pump is microseconds of decoding, Steam's
  own threads do the I/O, and the jobs seam's rule — pick a shape from
  `threaded()` once, at build time — would buy a second code path nothing needs.
- **Where it runs:** inside `Loop::frame_body`, beside `self.shell.pump(…)`,
  under its own `crcbl_core::trace::span` — it is work, unlike `wait_events`,
  which the loop keeps outside the frame span because idling is not work. But
  **not in slice 1**: the engine `Loop` grows a Steam limb when the second
  sample repeats the pattern, per the standing rule that a helper is extracted
  at the second caller. Slice 1 has the sample own `Steam` and call
  `pump`/`events` from its own frame, the `apps/bare` way. `crcbl::web::App`
  never changes — there is no Steam on wasm, and the crate has no items there.
- **Async calls are typed tokens redeemed at the pump**, the reply-stream
  discipline from topic 41 restated for a foreign pipe:

  ```rust
  /// A pending Steamworks call. Not `Copy`; redeeming consumes it.
  #[must_use]
  pub struct SteamCall<T: CallResult>(ApiCall, PhantomData<fn() -> T>);

  pub enum CallState<T: CallResult> {
      /// Not answered yet: the token comes back, poll next frame.
      Pending(SteamCall<T>),
      Ready(T),
      /// Steam reported I/O failure, or the payload did not decode.
      Failed(CallError),
  }

  impl Steam {
      pub fn take<T: CallResult>(&mut self, call: SteamCall<T>) -> CallState<T>;
  }
  ```

  Every method that returns a `SteamAPICall_t` registers it in the pending set
  as the only way to construct a `SteamCall` — so a completion for an id nothing
  registered can only mean the caller dropped the token, which is legal
  fire-and-forget, and the payload is dropped with a diagnostics count rather
  than an error. Type safety is the registry's job: the entry records the
  expected callback id (`iCallbackExpected`), `GetAPICallResult` is called with
  exactly that id and the expected size, and a size or id mismatch is
  `CallError::Decode`, not a reinterpret. Move semantics make double-redeem
  unrepresentable; `Pending` handing the token back makes polling from a frame
  loop natural — hold it in game state, try again next tick.

- **Unknown callback ids are skipped, not errors** — the opposite of the
  topic-41 rule, deliberately: that stream refuses unclaimed tags because both
  halves are ours and an unclaimed tag is corruption; this pipe is Valve's, it
  carries dozens of ids we never subscribed to, and every SDK update adds more.
  Skipping is the specified behaviour of the loop. What must not be silent is a
  _claimed_ id whose payload disagrees with our struct — that is SDK drift, and
  it lands in `pump` diagnostics (`decode_skips: u32` with the id and cause)
  that the local smoke gate asserts stays zero.
- **Callback payload decode is `repr(C)` structs with the platform's packing,
  size-checked before read.** Valve packs callback structs at 4 bytes on
  Linux/macOS and 8 on Windows (see the traps section); each bound callback is
  declared once with `#[repr(C, packed(4))]`/`packed(8)` selected by
  `cfg(target_os)`, a `const` assert pins `size_of` per platform to the value
  read from the SDK, `m_cubParam` is compared against it before the
  `read_unaligned` copy-out, and fields are only ever copied, never referenced.
  No bounds-checked byte reader à la `codec.rs`: these are not our wire format,
  they are C structs with a C layout, and restating them as offset arithmetic
  would be a second copy of knowledge the `repr` already encodes.

## Where Steam meets seams the engine already has

Each of these is the repo's standing architectural question — backend behind an
existing seam, or parallel API — answered per interface.

- **Cloud saves (`crcbl-store`): backend behind the seam — and the first step is
  no code at all.** Steam's Auto-Cloud syncs a configured directory without any
  SDK call; `crcbl-store`'s `NativeStorage::data(app)` layout plus
  `write_atomic` is already the shape Auto-Cloud wants (whole files, atomic
  replace). So the cloud slice is partner-site configuration before it is Rust.
  The API route exists for when per-file control is wanted: a
  `SteamCloudStorage: StorageSource` — five methods, and `StorageError` already
  carries `Pending` ("a state, not a failure — poll again next frame") and
  `Unsupported`, added for exactly this kind of backend. Parallel save API:
  declined; nothing above the seam may name Steam.
- **Identity and auth (topic 27): Steam is a tier-3 trust root the project does
  not have to operate.** The flat calls, verified:

  ```c
  S_API HAuthTicket SteamAPI_ISteamUser_GetAuthSessionTicket( ISteamUser* self, void * pTicket, int cbMaxTicket, uint32 * pcbTicket, const SteamNetworkingIdentity * pSteamNetworkingIdentity );
  S_API EBeginAuthSessionResult SteamAPI_ISteamUser_BeginAuthSession( ISteamUser* self, const void * pAuthTicket, int cbAuthTicket, uint64_steamid steamID );
  S_API void SteamAPI_ISteamUser_EndAuthSession( ISteamUser* self, uint64_steamid steamID );
  ```

  The seam already fits: `Hello` carries `session_token: Option<ResumeToken>`
  and `HandshakeGate` "does not generate credentials itself" — an `auth_ticket`
  field beside it, validated by a gate the server configures, is the same shape.
  Two honest caveats before this reopens tier 3. First, the _server_ side of
  `BeginAuthSession` wants the game-server API (`SteamGameServer_Init`,
  anonymous login — no user account needed on a dedicated server), which is a
  sibling init path this document scopes out to its own slice. Second, the
  validation _result_ is asynchronous (`ValidateAuthTicketResponse_t`), so the
  gate admits provisionally and the session layer must handle late rejection —
  which its reconnect machinery is already shaped for. `crcbl-mint` stays cut;
  Steam replaces the backend it would have been.

- **Networking (topic 23): a parallel `Transport` backend, later, and not a
  replacement.** `crcbl-net`'s `Transport` is message-oriented, non-blocking,
  caller-driven — `ISteamNetworkingSockets`' shape too, and
  `crcbl_store::replay::FileTransport` is precedent that other crates implement
  it. The value Steam adds is the two things topic 23's own UDP cannot do from a
  living room: NAT traversal and the SDR relay. But P13 (UDP, reliability, LAN
  discovery) is unbuilt, and its LAN scope was a deliberate 2026-08-09 decision;
  a `SteamTransport` slice waits until P13's seam is proven and a sample
  (towers, bracket) wants internet play. Recorded as deferred, not refused — the
  WebRTC precedent.
- **Steam Input (`crcbl-input`): declined for now.** `crcbl-input`'s seam is
  push methods on `ActionMap`, and topic 19 already commits to hand-FFI device
  backends (evdev P10, XInput/GameController P14). `ISteamInput` is not a device
  — it is a _competing action mapper_ with its own bindings UI; wrapping it
  means two places where "jump" is defined and two config formats fighting.
  Meanwhile Steam Input's gamepad emulation already reaches the planned backends
  as an ordinary controller. Revisit only if Steam Deck verification (which
  requires first-class Steam Input support) becomes a goal; that is a user
  decision with real scope, recorded below.
- **The overlay (rendering):** needs nothing wrapped — it injects into the
  present path (on Vulkan, a layer around `vkQueuePresentKHR`). **Whether it
  composites correctly over `crcbl-shell`'s from-scratch Wayland/X11 windows and
  `crcbl-vk`'s swapchain is unverified and stays a named line in the local smoke
  checklist**, not an assumption. The engine-side obligation is the standing
  one: pause-on-`OverlayActivated`, which is why that event is in slice 1.

## Slice order

Ordered by what the engine's samples would actually use, each slice shippable
and testable on its own. Interface accessor names per the mirror; re-read at
implementation.

1. **Lifecycle + pump.** The loader (`dlopen`, `symbol!`, `Lib`), `init` with
   the version handshake, `Drop` shutdown, `relaunch_via_steam`, the manual-
   dispatch pump, `SteamEvent` queue with `OverlayActivated`, the pending-call
   registry, `ISteamUtils`/`ISteamApps` basics (app id, UI language, overlay
   enabled), the fake-`Lib` test rig, the declaration-drift gate, the local
   smoke test under SpaceWar (app id 480). Consumer: `apps/sandbox` behind the
   umbrella's `steam` feature. Unlocks: "am I under Steam", overlay pause,
   language for future localisation — and every later slice.
2. **Identity + presence.** `ISteamUser` (`SteamId`, persona via
   `ISteamFriends`), rich presence set/clear, persona-change and join-request
   events. Unlocks: player names in samples instead of "player 2", invites
   groundwork.
3. **Achievements + stats.** `ISteamUserStats` — post-1.61 model, no
   `RequestCurrentStats`: `unlock`, `store`, stat get/set, the stored events.
   First real sample consumer: breakout's high score becomes a stat with an
   achievement. Unlocks: the first player-visible Steam feature.
4. **Cloud saves.** Auto-Cloud configuration documented against `crcbl-store`'s
   layout (code-free), then `SteamCloudStorage: StorageSource` over
   `ISteamRemoteStorage` if per-file control is wanted (decision below).
   Unlocks: saves that follow the player.
5. **Auth tickets (client half).** `GetAuthSessionTicket` /
   `GetAuthTicketForWebApi`, ticket lifetime (cancel on session end), the
   `Hello.auth_ticket` field and provisional-admit gate design with topic 27.
   Unlocks: tier 3 reopened in design; blocked on slice 6 for enforcement.
6. **Game-server API + ticket validation.** `SteamGameServer_Init` (anonymous
   login), `BeginAuthSession`/`EndAuthSession`, `ValidateAuthTicketResponse` →
   late-rejection path in `crcbl-net`'s session layer. Unlocks: tier 3 for
   dedicated servers, bans included, with Valve as the trust root.
7. **`SteamTransport`** over `ISteamNetworkingSockets` behind `crcbl-net`'s seam
   — after P13 exists and a sample wants internet play. Unlocks: NAT traversal
   and relayed connections for towers/bracket.
8. **Workshop (`ISteamUGC`)** — last: the largest surface, UGC handles and
   multi-step async flows, and its natural consumer is the editor/modding story
   (topics 8, 16), which is itself post-MVP.

## What CI proves, what it cannot, and how the gap stays honest

- **CI proves:** the crate compiles on all four targets with all features; the
  decode tables, packing-selected structs and their size asserts, the
  pending-call registry, and the pump's drain logic all pass unit tests — the
  pump is testable because `Lib` is a struct of function pointers, and a test
  constructs one from Rust `extern "C"` fns that feed scripted `CallbackMsg_t`
  sequences (the wrong-size payload, the unknown id, the completion nothing
  registered, the completion that must decode). That is the fake-`Lib` rig, and
  it exercises the real drain loop, not a copy.
- **CI cannot prove:** that the declarations match a real SDK, that init
  succeeds against a real client, that the overlay composites, that a ticket
  validates. Each has a named home instead of a green light: the
  declaration-drift gate and the smoke test are `#[ignore]`d tests run locally
  (`cargo test -p crcbl-steam -- --ignored` with `CRCBL_STEAM_SDK` set and Steam
  running under app 480) — ignored is the honest verdict, "not run here", never
  "passed"; this is the `local vk tests run on real hardware` arrangement
  repeated, and it gets the same memory-file treatment.
- **The fake cannot become production.** It is not a registered backend and
  there is no registry: production `Steam` values come only from `Steam::init`,
  whose only library source is `dlopen` of the real redistributable. The
  fake-`Lib` constructor is `#[cfg(test)]` inside the crate's own test support;
  no feature exposes it, so no `--all-features` build ships it and no game can
  select it by accident — a game must never silently think it is signed in, the
  same sentence the null-GPU test asserts. Games that want to run Steam-less do
  not fake Steam; they hold `Option<Steam>` and got `None` from an ordinary
  `Err`.

## The cases that are easy to get wrong

- **Callback packing differs by OS, and Valve says so in the header.**
  `steamclientpublic.h`: Linux/macOS/FreeBSD define `VALVE_CALLBACK_PACK_SMALL`
  → `#pragma pack(push, 4)`; everything else (Windows) `_LARGE` →
  `pack(push, 8)`, with the comment that 64-bit gcc would otherwise grow the
  structs past the 32-bit layout. A struct copied from a Windows-tuned binding
  is wrong on Linux and vice versa; the per-platform `packed(N)` + per-platform
  size assert is the guard, and the asserts must disagree across platforms for
  any struct containing a `u64` after an odd-count of `u32`s — if they all
  agree, suspect the assert.
- **Never reference a packed field.** `&msg.value` on a `packed` struct is
  undefined behaviour in Rust; every field access in decode is a copy
  (`read_unaligned` from the payload pointer, then plain moves). `cargo miri`
  over the decode tests is the escape-hatch rule from the workspace applied
  here, on the fake-`Lib` fixtures.
- **`GetNextCallback` without `FreeLastCallback` is a protocol violation**, and
  the borrowed payload dies at the free. The drain loop owns the whole sequence
  — decode-and-copy strictly between the two calls — and no borrowed payload
  escapes `pump`; nothing about this is exposed for a caller to hold wrong.
- **Never bind `SteamAPI_RunCallbacks`.** Manual dispatch and the classic path
  are mutually exclusive by documented rule. The strongest enforcement is
  absence: the symbol is not in `Lib`, so no code path can call it.
- **`SteamAPI_InitFlat` does not version-check.** Its own comment says so. Call
  `SteamInternal_SteamAPI_Init` with the accessor-version list; the detailed
  `SteamErrMsg` is for the log, the enum is for the match.
- **C string returns are borrowed from Steam's internal buffer** (e.g.
  `GetPersonaName`) and stable only until the next SDK call. The wrapper copies
  to `String` before returning, always; no `&str` of Steam memory ever crosses
  the crate boundary. Steam strings are UTF-8; decode is `from_utf8_lossy` with
  a diagnostics count on lossy, since a mangled nickname must not kill a frame.
- **`&str` → C string needs a NUL check**, and an interior NUL in an achievement
  name is an `Err`, not a truncation or a panic.
- **Stale recall of the auth signature.** `GetAuthSessionTicket` grew a
  `const SteamNetworkingIdentity *` parameter (verified above); bindings written
  from memory of the older three-argument form corrupt the stack on 32-bit and
  silently pass garbage on 64-bit. This is the concrete instance of the
  provenance rule: every declaration carries the SDK version it was read from,
  and the drift gate re-checks the lot.
- **Tickets leak.** Every `GetAuthSessionTicket` needs a `CancelAuthTicket`,
  every `BeginAuthSession` an `EndAuthSession`; both belong to session teardown,
  not to `Drop` of `Steam` (Steam cancels on shutdown anyway — the leak that
  matters is a long-lived process churning sessions).
- **`steam_appid.txt` inverts a guard.** With the file present,
  `RestartAppIfNecessary` returns false regardless — correct for dev,
  catastrophic if shipped, and invisible in every dev-machine test. The ship
  checklist, not code, owns this one.
- **App id 480 is shared.** SpaceWar's stats, achievements and cloud are
  everyone's test data; the smoke test asserts mechanisms (init, pump, events
  arriving), never values read back from 480.

## Decisions this document asks for

Recorded here in the backlog's format; they move to `docs/backlog.md` when work
is scheduled.

### DECISION NEEDED — binding route, and publishing our own flat-API declarations

Route (a) means this public MIT repo contains hand-written Rust `extern "C"`
declarations and `repr(C)` structs describing Valve's ABI — function names,
argument types, struct layouts, callback ids — authored by us, transcribing no
header text. The access agreement licenses the SDK source "solely to develop"
and does not contemplate this either way; the ecosystem precedent is strong
(Steamworks.NET has published exactly this, MIT-licensed with Valve's awareness,
for over a decade; `steamworks-sys` publishes bindgen output — and the SDK
itself — on crates.io), but precedent is not permission and this research read
the agreement, not a lawyer.

- **(a) Accept the posture and hand-write the declarations** — zero
  dependencies, loader semantics we control, the drift gate as the safety net.
  The recommendation.
- **(b) Depend on `steamworks-rs`** — the ABI risk becomes theirs; costs a
  link-time `DT_NEEDED` (no graceful absence), a vendored SDK in the dependency
  graph, an event-model mismatch to wrap over, and the workspace's first large
  foreign binding. A new dependency, so the user's call by standing rule either
  way.

### DECISION NEEDED — an app id of our own

Everything real beyond slice 1 (achievement definitions, stats schema,
Auto-Cloud config, rich presence localisation, game-server logins) is configured
per-app on the partner site, and SpaceWar cannot carry it. A registered app
means a Steamworks partner account and the app-credit fee, and names a product
decision — which sample, if any, is the thing on Steam (towers and bracket are
the candidates the sample ladder suggests). Until then, slices 2+ are built
against 480 with mechanism-only smoke tests.

### DECISION NEEDED — cloud saves: Auto-Cloud config or a `StorageSource` backend

- **(a) Auto-Cloud only** — zero code, uses `crcbl-store`'s existing atomic file
  layout; sync timing is Valve's (on exit), no in-game sync UI possible.
- **(b) `SteamCloudStorage` backend over `ISteamRemoteStorage`** — per-file
  control, quota introspection, conflict surfacing; a real slice of async code
  behind the seam. The plan's lean: (a) first, (b) only when a sample
  demonstrates a need Auto-Cloud cannot meet.

### DECISION NEEDED — Steam Input, or the topic-19 backends only

Declined above for the action-mapper conflict; the counterweight is Steam Deck
verification, which requires first-class Steam Input. If Deck is ever a target,
`ISteamInput` returns as a slice that feeds `ActionMap` through
`Binding::Virtual` — origins and glyphs included — and topic 19's backend table
gains the row with that justification. Until someone says "Deck", the P10/P14
hand-FFI backends stand alone.

## What this document does not settle

- **The `SteamEvent` variant set and the callback-id table.** They grow a slice
  at a time and live beside the decode code, where adding one touches one file —
  the topic-41 opcode-table rule.
- **The game-server crate question.** Slice 6 may want the game-server half in
  `crcbl-steam` behind a module or as `crcbl-steam-server`; the init paths are
  siblings, not nested, and the split is decided when the dedicated server
  (P13's headless build) is real.
- **`SteamTransport`'s design** — connection lifecycle onto `Transport`'s
  `is_connected`, message size caps against `TransportError::MessageTooLarge`,
  identity plumbing. Owed to the slice, written against a P13 that exists.
- **Overlay-over-own-windowing verification** — a smoke-checklist line until
  someone runs it; the answer decides nothing in this design either way, but a
  game shipping without a working overlay needs to know.
- **Exact interface versions** — pinned only when the first SDK is downloaded
  and the drift gate exists; the numbers in this document are the mirror's and
  are expected to move.
